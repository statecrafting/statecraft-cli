## 4. What §3.25 and §3.26 now do

### 4.1 The required identity, `crates/statecraft-home/src/required.rs`

The required identity is a **committed project requirement**, carried as one
key (`harness`) in the manifest's `project.requirements`. That map is the
governed contract for a committed requirement and it already binds every
configuration layer, so no personal default and no run choice may contradict
one; a second bespoke field beside it would have been a requirement the
requirement machinery did not know about. The committed value is the **full**
digest, and a short display identifier committed in its place is refused,
because an equality check against a truncation is not an integrity proof.

Seven standings. Only `exact` with a resolved revision permits managed
execution, and `permits_managed_execution` is a match with every arm spelled
out so a state added later has to decide rather than inherit `true`.

| Standing | When | Managed execution |
|---|---|---|
| `unrequired` | the project commits no requirement | refused |
| `malformed-requirement` | the committed value is not a full digest | refused |
| `missing` | no revision is installed under the required identity | refused |
| `corrupt` | one is, and its files no longer digest to it | refused |
| `unreadable` | the installed tree could not be read at all | refused |
| `mismatched` | a revision resolved and it is not the required one | refused |
| `exact` | required, installed, intact, and a revision resolved | permitted |
| `exact`, nothing resolved | required, installed and intact; no session has resolved against it | refused |

`unreadable` is distinct from `corrupt` on purpose: corrupt is an answer, and
unreadable is the absence of one. Both refuse, and only one of them says what
is wrong.

The last two rows are one variant and two questions, kept apart because they
have different answers. **Disagreement** is the diagnostic question and
`doctor` asks it: a project whose requirement is committed, installed and
intact disagrees with nothing, so it is not a finding whether or not a session
has resolved yet. **Refusal** is the execution question: a requirement nothing
has been resolved against is a healthy project and not a qualified session, and
reading an unasked question as an affirmative answer is the same defect as
reading a configured deny entry as an enforced one (§3.28).

**The two refusals §3.25 names are asserted, not intended.** Nothing selects
the latest installed revision: a home holding two revisions and a requirement
naming neither answers `missing`, and the refusal says why the installed ones
are not substitutes. Nothing populates the requirement during a read:
`evaluate`, `inspect` and `plan_upgrade` all take `&Manifest`, and a test
compares the manifest file's bytes before and after all three.

**Existing manifests are addressed explicitly.** A manifest written before
§3.25 carries no requirement, is `unrequired`, is **not** qualified, and is not
repaired by a read. The migration is an explicit upgrade, which is a reviewed
committed change.

**All four capabilities stay available under every refusal.** Inspection lists
what is required, what is installed and what each digests to. Diagnosis is a
new `doctor` finding, `harness-requirement`: the comparison needs a product
home, which the crate owning `doctor` cannot see, so it is made in the binding
and reported beside everything else the diagnostic found. Planning and applying
an upgrade are separate, so nothing commits a requirement as a side effect of
installing or running, and the plan reports whether §3.24's settings consent is
asked again.

Eighteen tests, one per row the owner named.

| Field | Source |

| instruction-file identities | each file the chain names, read now, by path and digest |

| adapter identity | name, harness, version |

The added evidence sits beside the verdict as three types that nothing
substitutes for one another.

| Class | Type | Says |
|---|---|---|
| 1 | `Delivery` | a rule was evaluated against the tree and arrives |
| 2 | `Supply` | the bytes were read, digest to what is recorded, and were handed over |
| 3 | `Observation` | a running session was observed behaving as required |

`Supply` distinguishes a delivery that **failed** part way, carrying what had
been supplied when it failed, from one **never attempted**. `Observation`
reaches `Observed` only through `from_qualification` on a
`session::Qualification::Qualified`, or through `admit` (§4.3): no digest, no
file read and no version probe can produce one. `qualifies()` is a conjunction
of all three plus §3.25's standing, with no shortcut.

**Absent evidence is not success.** `incomplete()` names every field a record
may not be written without; `write` refuses an incomplete record and writes
through a rename, so no reader sees half of one; a truncated record reads back
as an error rather than as no record. Two internally contradictory shapes are
refused: `reached` with no chain, and a verdict that did not arrive carrying
the chain it would have arrived by. A chain naming a file the tree no longer
holds is refused at assembly rather than recorded as a shorter chain.

No field claims a model **read**, **understood** or **complied with**
anything, and a test asserts those three words are absent from the serialized
record.

Records live under `.statecraft/state/startup/`, which is ignored, beside the
frozen run resolutions. The committed half of §3.25 is the requirement, and
only the requirement. Twenty-one tests.

### 4.3 How a live observation is admitted

**The four-check admission this section described is gone.** It read the
provider's prose for the refusal, and §3.29 records the sentence that defeated
it. `startup::admit` now delegates to `crates/statecraft-home/src/admission.rs`,
which reads the harness's own `permission_denials` record through the types
spec `004` already owns, and which requires three controls rather than one
capture. §3.29's six rules are the contract and the module header is the
reasoning; what matters here is that

- the refusal is a **structured denial** whose `tool_input` names the claimed
  command, never a sentence containing it;
- the allowed-command and absent-payload controls are **conditions on the
  evidence**, enforced by the boundary, not steps in this document;
- the claim is bound to its invocation, its settings bytes, its payload digest
  and the version the capture itself reports;
- **every route runs the same admission**, deserialization included: the
  observation carries its evidence, `qualifies()` re-judges it, and a record
  whose observation no longer admits itself is refused at the write.

A claim that is not admitted writes **nothing**, because a record carrying a
rejected claim as an absence would lose the fact that a claim was made and
refused.

What it still does not establish is in the module header and is worth repeating
here: it establishes what the captured bytes show, not that they came from a
provider. That residual is why the bytes are kept in the record.

**Superseded in part on 2026-09-22 by §3.30.** The admission described above
treated a tool-use **request** with no denial entry as a control that ran,
matched a denial to its command by text alone, kept only the last init and
terminal events, and bound the invocation to its settings by token presence in
an argument list the caller wrote. Nine one-mutation probes of those defects
were all admitted at `88bc616`. The repair (`bc0b5a5`) classifies each tool use
as refused or executed by correlating request, result, denial entry,
mid-stream denial and the harness's `non_execution_kind` note; reads a capture
as one session; judges process end and terminal state per control; and checks
each invocation against the **launch record** `startup capture` writes, by
recomputing the exact argument vector. The record's trust boundary is
launcher-attested, not provider-authenticated, and a synthetic capture never
qualifies.

### 5.2 Correction: the hooks do inspect the index, and the gate was skipping

**The previous revision of this file was wrong.** It recorded staged, unstaged
and untracked derived output as a coverage gap, on the grounds that the shipped
hooks never inspect the index, so the three states would be indistinguishable
and a test would assert a property of `git`. `statecraft-pre-bash.sh` reads
`git diff` for the unstaged state, `git diff --cached` for the staged one and
`git ls-files --others` for the untracked one, on three separate lines.

Reading the same path found a second defect. Where `spec-spine config show
--json` did not report the derived directory, the hook printed
`derived-tree check skipped` and **continued**, citing the counterparty's spec
`093` section 3.4. That conflicts with the rule this corpus adopted: §3.23
contract 6 says a gate whose check did not run is not green, and the Stop
policy's second part says an enforcing operation gate refuses a failed **or
unavailable** check. This gate stands in front of `gh pr create` and is the one
hook §3.23 marks enforcing. The adopted rule wins, the inherited wording is
recorded as the conflict it is in §5 of the spec, and the weaker behavior is
not preserved merely because it was copied. The three git reads also discarded
their exit statuses, so a failed read was indistinguishable from a clean tree;
each status is now read.

Seven behavioral cases cover it, all running the hook as a program:

| Case | Asserts |
|---|---|
| `the_derived_tree_check_passes_a_tree_whose_shards_are_committed` | the positive control, without which the six refusals prove nothing |
| `an_unstaged_derived_change_refuses_the_pull_request` | refused, named as unstaged, file named |
| `a_staged_derived_change_refuses_the_pull_request` | refused, named as staged, **not** as unstaged |
| `an_untracked_derived_file_refuses_the_pull_request` | refused, named as untracked, file named |
| `a_staged_change_cancelled_by_the_working_tree_is_still_refused` | both states named; the premise that HEAD alone sees nothing is asserted first |
| `a_failed_derived_read_refuses_rather_than_reading_as_clean` | `NOT PERFORMED`, and the message distinguishes it from a clean tree |
| `an_unanswered_derived_directory_refuses_rather_than_skipping` | all three shapes an unanswered configuration takes |

The two behavior-change cases were run against the **unamended** hook and fail
there. The four state cases pass against both, which is what restoring a
missing test looks like rather than writing a new requirement.

Every hook run is now isolated from the operator's own configuration as well as
from their `spec-spine`: `HOME` is the fixture's, and git is told to read
neither the global nor the system configuration, so an operator's
`core.hooksPath`, their `includeIf` blocks and their own global hooks cannot
reach into a measurement of this product's. Where running the hook is part of
the claim, the stub's witness is asserted nonempty.

## 6. The acceptance, as separately authorized stages

**Approving one does not approve another**, and the script enforces it: each
gate refuses with exit 2 when unset, and the provider approval does not satisfy
the coexistence gate. The local route never reads the provider approval, marks
every capture synthetic, and reports **ADMITTED (SYNTHETIC)** at best.

### 6.2 What a run bounds

The three sessions run in order (refusal, allowed command, absent payload),
each under the product's own process-group supervisor with a `STEP_TIMEOUT`
deadline (300 seconds by default) and each preceded by a 30-second version
probe. The first launch that does not complete ends the stage with **no
further session**: there is no retry, no replay, and no extra session. Every
local step is bounded by `LOCAL_TIMEOUT` with its whole process tree killed at
the deadline, and its status is recorded as `exit N`, `signal N` or `timeout
after Ns`, never collapsed into one number. Standard output and standard error
are kept apart everywhere.

### 6.3 What the preflight establishes before anything is paid for

The product (built, or named by `CLI`); a disposable project with no git
remote; a product-generated environment; the requirement committed by
`harness upgrade` and read back as `exact`; the payload recorded; the refused
command's `statecraft-absent` path confirmed absent; the unobserved record
written and `qualified false`. And, through the same launch and admission path
stage 2 uses, a local executable that prints §3.29's sentence is launched three
times, marked synthetic, and submitted: the preflight fails unless the
admission refuses it **as prose**.

### 6.4 Why every control is harmless if enforcement fails

| Control | If it is not refused |
|---|---|
| `cargo publish --dry-run --manifest-path statecraft-absent/Cargo.toml` | the manifest path does not exist, so cargo stops before resolving anything, searches no ancestor directory, and contacts no registry; `--dry-run` never uploads in any case |
| `echo statecraft-allowed-control` | prints a word |

Each launch grants exactly those two commands with `--allowedTools`, so an
improvised variant is not granted. After the three sessions the fixture project
must be unchanged (`git status --porcelain` empty), checked on disk rather than
read from a transcript.

### 6.5 The premises the live stage tests rather than assumes

Two design facts in §3.30 are premises and have not been observed on a live
provider here: that the provider accepts two space-containing rules after one
`--allowedTools`, and that its deny entry prevails over such a grant. If either
fails, the evidence shows it (the absent-payload control is refused, or the
refusal control executes) and the claim is refused as unverified. Neither
failure can produce an admitted observation.

Graded on 2026-09-22 without a provider session (spec `002` §5 records the
detail): both are **documented** by the provider and **read statically** from
the installed 2.1.267 binary, and the first is **locally exercised** against a
transcription of that binary's splitter. Neither is **observed**; only this
stage can observe them.

### 6.6 What makes a run unverified, and why that is a result

A launch that does not complete, or captures the admission refuses, end the
stage with **UNVERIFIED** and exit 1, with the captures kept for review. That is
§3.29 rule 6. Captures that cannot be read at all are exit 4, because no claim
was judged. The floor is not lowered, the admission is not loosened, and no
repository-local harness copy is written to hide the limitation.

### 6.7 What the script's own tests cover

`crates/statecraft-cli/tests/acceptance_script.rs` runs the script as a program
with a fake provider, in a directory whose name holds a space, both quote kinds,
a backslash and a dollar sign: a synthetic admission, a provider that ignores the

conflicting output, a timeout with a descendant, a signal, an unreadable version,

### 6.8 Cleanup

Nothing is removed automatically, because stage 2 needs what stage 1 built:
the earlier version removed the preflight's directory on exit, so stage 2 could
never find it. `clean` removes `$ACC` only when it carries the script's marker,
